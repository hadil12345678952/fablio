### 1.1 Architecture comprise et confirmée

```
Navigateur (fr, enfants 7-10 ans + enseignant)
   │  pages : composants serveur RSC + 21 composants clients
   ▼
Next.js 16 App Router  ──  src/middleware.ts (NOUVEAU : contrôle d'origine /api/**)
   │  31 routes API (42 méthodes) — aucune logique métier dans les contrôleurs
   ├── src/lib/api.ts ........... corps/erreur/origine publique + 429 (NOUVEAU)
   ├── src/lib/auth.ts .......... sessions en base, bcrypt, cookie httpOnly
   ├── src/lib/securite.ts ...... bornage anti-force-brute (NOUVEAU)
   ├── src/lib/exercices.ts ..... moteur de notation des 8 types (pur, testable)
   ├── src/lib/blocs/* .......... moteur de parcours (registre, validation, service)
   ├── src/lib/statistiques.ts .. agrégats + export CSV
   ├── src/lib/medias.ts ........ normalisation Drive/Dropbox/YouTube/Vimeo/H5P (pur)
   └── src/lib/courriel.ts ...... Resend sans SDK, repli journal, idempotence
   ▼
PostgreSQL (Neon en prod) via Drizzle ORM + pg.Pool — 10 tables, 28 index
```

Quatre qualités structurelles **vérifiées dans le code**, à préserver dans toute
suite de développement :

1. **Le contrôle d'accès est en une seule porte** : `enseignantConnecte()` /
   `eleveConnecte()` (`src/lib/api.ts`) appelées par **les 31 routes**. Aucune
   route ne fait exception (vérifié par balayage : les seules sans session sont
   `health`, les 7 routes d'authentification, et elles sont volontairement publiques).
2. **Le cloisonnement multi-enseignants est systématique** : chaque requête est
   filtrée par `enseignant_id`, et la soumission d'exercice vérifie la
   **propriété de la fable** *et* le ciblage de classe (vérifié par la section 5
   de la suite E2E : un élève d'une autre classe reçoit 403, jamais les données).
3. **La logique métier est isolée en modules purs** (`exercices.ts`, `medias.ts`,
   `blocs/validation.ts`) sans import de Next : notations et normalisations sont
   testables sans serveur — c'est ce qui a permis de prouver le moteur de notation.
4. **Les écritures concurrentes sont verrouillées** : `FOR UPDATE` +
   renumérotation dans une transaction pour les parcours par blocs.

### 2.1 Constat d'hygiène juridique

Le README annonce « **Projet open source** » alors qu'**aucun fichier `LICENSE`
n'existe** dans le dépôt. Sans licence, le code est « tous droits réservés » par
défaut : la mention du README est trompeuse pour un réutilisateur, et un
établissement ne peut pas légalement dériver le projet. **Recommandation R1** :
choisir et ajouter la licence (MIT ou Apache-2.0 côté code ; CC-BY ou
CC-BY-SA pour les contenus pédagogiques créés par les enseignants, qui posent une
question distincte — leurs fables et leurs exercices leur appartiennent).

## 3. Ce qui a été développé sur cette branche

### 3.1 Anti-force-brute (`src/lib/securite.ts`, table `tentatives_connexion`)

| Choix | Justification |
|---|---|
| Compteur **en base**, pas en mémoire | Vercel exécute plusieurs instances serverless : un `Map()` ne serait ni partagé ni persistant, et un attaquant chaufferait le froid pour réinitialiser son compteur |
| Écriture atomique `INSERT … ON CONFLICT DO UPDATE` | Deux requêtes simultanées ne peuvent pas se lire en retard : pas de « time-of-check/time-of-use » |
| Consultation **avant** bcrypt | Le hachage est coûteux **par conception** : ne jamais le rendre gratuite à déclencher en boucle |
| Clé = SHA-256 de l'identifiant | Aucun email, aucun pseudo d'élève en clair dans cette table (RGPD/loi locale : minimisation) |
| Enseignant 5 échecs/15 min → 10 min ; élève 5/10 min → 5 min, **clé = code+pseudo** | Un élève qui se trompe ne bloque pas les 29 autres de sa classe |
| Fenêtre glissante + purge à la réussite | Un enseignant qui a échoué 4 fois il y a une heure repart de zéro ; la table ne grossit pas |
| **Dégradation ouverte** par défaut + `FABLIO_CONNEXION_STRICT=1` | Un outil de classe ne doit pas enfermer 30 élèves parce qu'une migration manque. Choix explicitement documenté dans le code et dans `/api/health` |

**Preuves d'exécution** : 5 échecs → 401 ; 6ᵉ requête **avec le bon mot de passe** →
429 `retry-after: 600` ; autre compte → 200 ; camarade de la même classe → 200 ;
table renommée (déploiement sans migration) → 401/200 normaux, **aucune
exception**, `/api/health` → `bornage:"indisponible (table manquante ?)"` et
`schemaManquant:["tentatives_connexion"]`, avertissement journalisé **une seule
fois** ; après restauration du schéma → `bornage:"actif"`.

### 3.2 Contrôle d'origine CSRF (`src/middleware.ts`)

En un point central (aucune des 31 routes à modifier), les méthodes mutantes de
`/api/**` doivent présenter un `Origin` dont l'hôte correspond à celui de la
requête ; les requêtes sans `Origin` (curl, apps natives) restent admises ; les
GET ne sont pas filtrés ; la comparaison ignore port et protocole pour ne pas
casser les proxies TLS ni les domaines d'aperçu Vercel. **Preuves** : POST et
DELETE inter-site → 403 avant toute base ; same-origin, sans `Origin`, GET et
pages → comportement inchangé (6 vérifications, section 20).

### 3.3 Chaîne de build Vercel fiabilisée (`vercel.json`, `scripts/vercel-build.mjs`)

* `installCommand: npm ci` → build reproductible sur lockfile verrouillé (validé : 444 paquets) ;
* `buildCommand: node scripts/vercel-build.mjs` → **pousse le schéma uniquement en
  `VERCEL_ENV=production`**, jamais depuis un aperçu, avec forçage explicite par
  `FABLIO_SCHEMA_PUSH=1|0` et message de remédiation si le push échoue (cas connu
  « `Interactive prompts require a TTY terminal` ») ;
* `functions.maxDuration` pour `/api/tts` (60 s) et l'export CSV (30 s).

**Preuve de non-régression du schéma** : `npx drizzle-kit push` sur une base
**vierge** crée 10 tables et 28 index **sans jamais poser de question** (exit 0) ;
relancé sur la base de démonstration → `[i] No changes detected` ; comparaison
`setup-db.mjs` ↔ `drizzle-kit push` : **aucune** différence de colonnes ni d'index.

### 3.4 Polices auto-hébergées (`src/app/polices/`, `next/font/local`)

Constat : `next/font/google` faisait **échouer le build hors connexion**
(`Failed to fetch 'Nunito' from Google Fonts`) — un build dépendant d'un hôte tiers
n'est pas reproductible — et faisait partir chaque classe vers Google à chaque
première page. Les 15 fichiers `.woff2` réels sont désormais versionnés (308 Ko)
et servis par le site avec `Cache-Control: public, max-age=31536000, immutable`.
Preuves : build **sans aucune simulation réseau** ✓ ; 18 règles `@font-face`
(15 graisses + 3 faces de repli ajustées métriquement) ✓ ; `/_next/static/media/…woff2`
→ 200 `font/woff2`, 18 920 octets ✓ ; **aucune** occurrence de `fonts.googleapis.com`
dans le bundle ✓ ; variables `--font-titre/--font-corps/--font-lecture` inchangées
et aucune famille codée en dur dans `globals.css` ✓.

### 3.5 Pureté du rendu React et qualité statique

Les 15 erreurs ESLint (règles du compilateur React) n'étaient **pas cosmétiques** :

* `src/components/blocs/rendu-parcours-fable.tsx` : le numéro d'exercice était
  porté par un `let` **muté dans le `.map()` du JSX** — un re-rendu repartait du
  compteur déjà incrémenté (numérotation qui dérive). Remplacé par une passe de
  calcul avant le rendu, comportement affiché identique ;
* `gestion-exercices.tsx` : `useRef(Math.random()…)` **pendant le rendu** (graine
  de mélange de l'aperçu) ;
* `joueur-exercice.tsx` : `useRef(Date.now())` pendant le rendu — le chronomètre
  d'une tentative pouvait démarrer au moment d'un re-rendu sans rapport avec
  l'action de l'élève (durées statistiques faussées) ;
* 11 apostrophes droites échappées → apostrophes typographiques `’` (corrige la
  règle **et** la typographie française).

Résultat : `eslint .` **0 erreur** (les règles de pureté React peuvent désormais
rester actives et bloquer une régression future), `tsc` 0 erreur.

### 3.6 Suite de tests rendue rejouable (lacune **découverte en travaillant**)

En exécutant deux campagnes E2E à quelques minutes d'intervalle, une vérification
**préexistante** a commencé à échouer :

```
✗ code de classe inconnu → 401 — reçu 429
```

Ni régression du code ni test faux négatif : mon bornage anti-force-brute compte
les échecs **par identifiant pendant 10 à 15 minutes**, et la suite utilise des
identités **stables** de la démo (`lina`, `CODE-BIDON`) pour ses sondes négatives.
Après quelques exécutions dans la fenêtre, la sonde se voyait refuser l'accès avant
même d'être évaluée. **Un compteur de sécurité change le contrat des tests : il
faut le traiter, pas abaisser le seuil.**

Correction : `tests/hygiene-base.mjs`, branché **au début et à la fin** de la
campagne — vidage de `tentatives_connexion` (les sondes redeviennent
déterministes) et suppression des comptes-jetons portant le `SUFFIXE` de la
campagne. Le module est **concessif** : sans `DATABASE_URL` (suite lancée contre
un déploiement de prévisualisation, sans accès à sa base), il avertit et la suite
continue en HTTP seul. Il n'introduit **aucune** dépendance (pilote `pg` du projet,
`dotenv` déjà requis).

Effet de bord réglé au passage : les comptes-jetons s'accumulaient (19 enseignants
`*.@fablio.test` après quelques campagnes) et `scripts/reinitialiser-demo.mjs`
**refusait** alors légitimement d'agir (« 5 enseignant(s) hors périmètre détecté(s) ») :
il fonctionne de nouveau. Vérifié : après nettoyage, `npm run demo:reset --
--confirmer` rend la base **identique au seed** — `enseignants=1 · eleves=3 ·
fables=3 · exercices=9 · blocs=16 · tentatives=23 · sessions=0 · bornage=0` — et
**deux exécutions consécutives de la suite donnent 138/138**.

### 3.7 Visuels de démonstration versionnés

`public/` était absent du dépôt : l'accueil journalisait « The requested resource
isn't a valid image for /images/hero-livre-magique.png received null » et les
illustrations du seed renvoyaient 404. Quatre aquarelles de démonstration (576 Ko
au total, ratios choisis pour éviter tout recadrage CSS) sont versionnées, et la
**section 21** de la suite échoue désormais si le dépôt perd ses visuels.
Ces images sont des **tampons** : à remplacer sous les mêmes chemins.

## 5. Préparer le déploiement de prévisualisation Vercel

### 5.1 Ce que la branche garantit déjà

* `npm ci` + lockfile verrouillé : mêmes paquets qu'ici, **0 vulnérabilité** connue ;
* build **sans accès réseau sortant** (polices auto-hébergées) : plus de panne
  aléatoire sur `fonts.googleapis.com` ;
* **aucun effet de bord** de schéma depuis un aperçu (le push ne court qu'en
  production) ;
* `DATABASE_URL` absente ou base injoignable : le build **passe** (les pages sont
  dynamiques, `/api/health` répond `ok:false`) — un aperçu reste consultable.

### 5.2 Variables à définir dans Vercel pour l'aperçu

| Variable | Production | Aperçu | Remarque |
|---|---|---|---|
| `DATABASE_URL` | pooled Neon | **branche Neon isolée** (R2) sinon la démo d'un aperçu écrit dans la production | avec `?sslmode=require` |
| `NEXT_PUBLIC_URL_SITE` | domaine final | URL de l'aperçu (ou laisser vide : `originePublique()` suit `x-forwarded-host`) | liens de courriel corrects |
| `RESEND_API_KEY`, `COURRIEL_EXPEDITEUR` | domaine vérifié | **ne rien mettre** : le lien part au journal, le test reste complet | jamais la clé de prod sur un aperçu |
| `OPENAI_API_KEY` | facultatif | idéalement absente (sinon facturation par les aperçus) | repli : TTS Google puis voix du navigateur |
| `PG_POOL_MAX` | 5 par instance | 2 sur un aperçu | pooler Neon |
| `FABLIO_CONNEXION_LIMITATION` | — | `off` si vous menez des tests de charge sur la connexion | sinon 5 échecs = blocage |
| `FABLIO_SCHEMA_PUSH` | non requis | `1` **uniquement** avec une base d'aperçu isolée | défaut : production seulement |

## 6. Recommandations d'architecture pour la suite du produit

1. **Garder la séparation observée** « route fine → `lib/` métier → Drizzle ». Les
   31 routes font 15 à 45 lignes et ne contiennent ni SQL métier ni validation
   maison : c'est ce qui a permis d'ajouter bornage, CSRF et diagnostic **sans**
   toucher aux 31 fichiers.
2. **Le registre de blocs** (`src/lib/blocs/registre.ts`) est le bon point
   d'extension pour les nouveaux types (document, quiz enrichi, galerie, export
   PDF du parcours) : un type = une entrée de registre + un éditeur + un
   validateur, sans migration de schéma (le contenu est du JSONB typé).
3. **Ajouter les types d'exercices dans `TYPES_EXERCICES` + `noterExercice`** : le
   moteur est une fonction pure avec un test par type — toute nouvelle notation
   doit arriver avec son cas dans la suite (comme pour les 8 actuels).
4. **Ne pas déplacer de logique métier dans le `middleware`** : le `middleware.ts` actuel reste sur
   l'edge (contrôle d'origine seulement, aucune lecture de cookie/base) pour ne
   pas payer une connexion PostgreSQL par requête. Ne pas y déplacer `lireSession()`.
5. **Le multi-tenant par enseignant est la bonne frontière** : avant d'ajouter une
   notion d'établissement ou d'administrateur, introduire une table `etablissements`
   + une vue « classe » matérialisée pour les statistiques, sinon `statistiques.ts`
   deviendra le goulot (R8).
6. **Verrouiller la qualité** : ajouter en CI (`R9`) `tsc`, `eslint` (0 erreur
   maintenant, donc franchissable en bloquant), `next build` et la suite E2E.
